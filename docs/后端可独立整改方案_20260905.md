## 2. 后端整改分项方案（L1：契约加固，建议第一批）

### 2.1 RUN-01/RUN-04 后端侧：失败与跳过不得伪装成“0 风险”

**证据（仓库侧）**
- `api.py:1502~1505`：review 初始值为全 0 对象（`total_rules=0/passed=0/failed=0/issues=[]`）。
- `api.py:1725~1729`：非可审查类别或无 GIS 图层时走“跳过审查”分支，只追加 warnings，最终仍 `status="success"`（`api.py:1773`）。
- `api.py:1718~1723`（规则执行异常路径）：异常追加进 `errors` 后流程可继续，最终仍可能返回 `success=true`；`api.py:1646~1650` GIS/SAFE 模块异常被 `except: pass` 完全吞掉。
- `schemas.py:27` DataPipelineResponse 无 `stage/stage_results/review.status` 等机器可读阶段字段，DSL 只能自己“猜”。

**建议改动（本仓库内）**
1. `review` 增加机器字段：`status`（`executed / skipped / error`）、`executed`（bool）、`reason`（中文原因）、`error`（可选）。跳过/异常分支统一写入，不再只靠 `total_rules=0` 表达。
2. `DataPipelineResponse` 增加可选顶层字段 `stage_results`（或 `stage`），明确 `data_pipeline` 已执行到的阶段（parse/review/…），并区分 `success`（HTTP/流水线级）与 `review.status`（业务阶段级）。
3. 规则执行异常（含 GIS/SAFE 子模块）不再 `except: pass`；必须写入 `errors`/`review.error` 且把 `review.status=error`。对“必需审查阶段失败”是否把顶层 `success` 置 false，建议按接口定位决定：`/agent/data-pipeline` 可保留 `success=false` 更安全。
4. 补充接口契约测试：覆盖“跳过审查”“规则异常”“无 review 载荷”“计数与明细不一致”四类输入，断言 DSL 不再能从空计数推断“无问题”。

**影响文件**：`schemas.py`、`api.py`（data_pipeline 主流程与异常分支）、`tests/test_data_pipeline_contract.py`（现有断言写死了 `review` 键集合，需同步扩展）、`api_docs.md`/`docs/04_FastAPI接口说明.md`。

**验收**：跳过审查时 `review.status="skipped"`；规则异常时 `review.status="error"` 且 errors 非空；DSL 即使忽略新增字段也至少不再看到“全 0 成功”的歧义载荷。

> 注意：RUN-01/04 的最终闭环仍需总控 DSL 解析节点读取这些字段；本项解决后端侧“发得出正确信号”，不替代 DSL 修改。

### 2.2 CON-03/CON-04 后端侧：BOM 行输出规范键与对象 ID

**证据（仓库侧）**
- `design_parser/bom_builder.py:210~219`：每行 BOM 使用中文字段（`最终数量`、`对应设计对象`、`单位`…），没有 DSL/施工端可稳定读取的 `quantity/unit/source_object_ids` 规范键。
- 审查报告 AUD-12 复现：施工端只读 `数量/quantity`，因此拿到真实 `/agent/bom` 输出（只有 `最终数量`）时材料数量为空。
- `api.py:1708~1716` 已有“按 code 前缀长度倒序匹配 object id”的实现可复用，说明对象 ID 可从 engineering_data 中回查。

**建议改动（本仓库内）**
1. `bom_builder.build_bom` 每行同时输出：
   - 兼容旧键（`最终数量`、`单位`、`对应设计对象`…）；
   - 规范键 `quantity`（=最终数量）、`unit`、`design_quantity/loss_quantity/reserve_quantity`、`material_code`、`source_object_ids`（对象 ID 数组）、`confidence_status`、`data_source`。
2. `source_object_ids` 在 `add()` 汇总行（如“6条光缆”）上尽量给出真实对象 ID 列表，无法精确归因的固定项输出 `[]` 并保持 `confidence_status=\"待人工确认/项目固定项\"`。
3. 接口文档明确“`quantity` = 旧 `最终数量`”的唯一换算，删除施工端对多种别名的猜测。
4. 补测试：断言旧键新键值一致、`quantity` 为数值、固定项 `source_object_ids=[]` 不误伤。

**影响文件**：`design_parser/bom_builder.py`、`api_docs.md`/`API_SAMPLES.md`、`tests/test_bom_builder.py` 等。

**验收**：同一 BOM 响应中 `quantity == 最终数量`、`unit == 单位`；施工端按 `quantity/source_object_ids` 可完整取数。

> CON-03/04 最终闭环需要施工指令工具（DSL 内嵌）改为读取规范键并精确匹配对象 ID；后端只负责把字段发对。

## 3. 后端新增能力（L2，需先决策）

### 3.1 FIB-01~05：确定性纤芯分配接口（FIB-03 的前提决策）

**现状**：本仓库没有“纤芯分配接口”，只有 `rule_engine.py:3047 build_fiber_assignments` 预置占用（按 1~N 连续芯假设），以及 R-FIBER 重复占用规则。审查指出的“已用 24 芯仍新增 4 芯”“芯 2 占用后选 1、3 而非连续 3、4”等缺陷全部位于 Dify `纤芯分配工具（PROD）.yml` 内嵌 Python 节点。

**两条路线**（需团队选择，未执行）：
- 路线 A：仓库新增确定性服务（如 POST /agent/fiber-allocation），接收 `engineering_data` + 业务参数，输出逐段候选分配/占用校验/冲突明细，并把聚合占用与逐芯表一致性校验做进后端；DSL 改为调用该服务。工作量大，但能把 FIB-01~05 的确定性逻辑收进可测仓库。
- 路线 B：不做新服务，明确当前工具只是“PCP 样例逐段候选分配”，由 111/PPT/技术书删除端到端、ODF 承诺；后端只保留 `build_fiber_assignments` 并把它改名为/文档化为“占用预置生成器”，同时补一致性校验回归测试。

**决策前不实现**：任何“复杂算法”或新端点。

### 3.2 BOM-01/REL-01：主链 BOM 身份决策（先选唯一主链）

- 若团队确定主链使用本仓库 `/agent/bom`（`api.py:263`），后端整改重点是 2.2 的契约规范 + Release 版本记录，不新增算法。
- 若主链维持 Dify `/v1/workflows/run`，独立 `BOM工具（PROD）.yml` 不是后端整改对象，后端只配合字段契约。
